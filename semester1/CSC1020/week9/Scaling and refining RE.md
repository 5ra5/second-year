# Tailoring Characteristics for RE
- Project setting - size, budget, time constraints, number of people, overall software development process
- Knowledge of the team - different skill sets
- Stakeholders
- Type of system
- System Characteristics
- Business & legal concerns

Minimalist RE - less than 10 developers
- User stories
- System vision
- Quality requirements

Template for user stories
```
As a <user role>
I want to <desired system feature>
So that <value/benefit>
```

Medium RE - 5 to 20 developers
Large RE  - over a 100 developers

# Refining Requirements

 Iterative in practice:
- Start with: project scope, business case analysis, domain model, stakeholders, system vision, goal model
- Elaborate with others including usage model
- Check back whether other artefacts need to be updated
- Go back and update the information during design if needed

Iterative nature of this action requires us to communicate with the rest of the team to continue developing our part of the project.

TRACEABILITY IN RE
- In a software company setting, developers deal with other people's code - software archaeology
- Same in RE - we need to be able to trace and match all things we mention in the SRS document
- PowerPoint , Excel, database, CASE - most frequently used for this (ordered by traceability)
- Excel is a better tool to get more specific in requirement engineering
- Requirements Database would be an even better option than Excel because it allows complex search for Requirements we're looking for
- CASE (Computer-Aided Software Engineering) - (jama, ReqSuite, Xebrio ...)

UML Conventions
- nodes are objects
- edges are lines that connect them to explain their relationship
- we use nodes and edges in most UML diagrams
