# What you will do

-  UML class diagram for a software system
-  design the structure of the system, do not implement it
-  UML class diagram on paper (A4 or A3)

-  how objects interact
-  how responsibilities are distributed
-  how the system can be extended in the future
-  how to organise classes so that the design stays clean and understandable

## what your diagram must include

-  classes / abstract classes / interfaces
-  hierarchy / composition / aggregation
-  meaningful **attributes and methods**
-  clear relationships between classes

the diagram clearly represent how the system works conceptually
you are not writing java code, but your design should be realistic

## what you should think about

-  which class is responsible for what
-  should this be an interface or an abstract class
-  should these objects inherit from each other or contain each other
-  which class coordinates the system
-  how to handle extensions

-  avoid creating a single god class that does everything

## deliverable

-  **one UML class diagram**
-  drawn on **A4 or A3 paper** (A3 recommended - you can glue 2 A4's together)
-  clearly labelled
-  **readable**


your diagram should include:
-  class names
-  important attributes
-  key methods

## what you should NOT do

-  write implementation code
-  draw extremely detailed method lists
-  invert dozens of unnecessary classes
-  create meaningless relationships just to increase class count
