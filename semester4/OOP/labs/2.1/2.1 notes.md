**object-oriented programming** = programming paradigm that provides a means of structuring programs so that properties and behaviours are bundled into individual objects

example: a person will have properties like name, age and address and behaviours like walking, talking, breathing and running

example: an email will have properties like recipient list, subject and body and behaviours like adding attachments and sending

so, properties are like parts of something that we define, and behaviours are functions, so they are actions that the object can do/take

**four pillars of OOP**
1.  **encapsulation** = bundling data(attributes) and behaviours(methods) within a class to create a cohesive unit
2.  **inheritance** = creation of hierarchical relationships between classes, allowing subclasses to inherit attributes and methods from the parent class
3.  **abstraction** = hiding implementation details and exposing only the essential functionality  of an object
4.  **polymorphism** = treating objects of different types as instances of the same base type, as long as they implement a common interface or behaviour

defining a class in python
```python
class Employee:
	def __init__(self, name, age):
		self.name = name
		self.age = age
```

-  classes define functions called methods, which identify the behaviours and actions that an object created from the class can perform with its data
-  a class is a blueprint for how to define something
-  while the class is the blueprint, an instance is an object that's built from a class and contains real data

**dog class example**

-  indent the `.__init__()` method's signature by 4 spaces, and the body of the method by 8 spaces
-   **instance attributes** = attributes created in `.__init__()`, they are dynamic and more than probably different for each instance
-  **class attributes** = attributes that have the same value for all class instances, you define them directly beneath the first line of the class name and indent them by 4 spaces - you always need to assign an initial value.
```python
class Dog:

	species = "Canis familiaris" # class attribute
	
	def __init__(self, name, age):
		self.name = name
		self.age = age
		
	def bark(self):
		return f"{self.name} says woof!"
		
	def play_with(self, other_dog):
		return f"{self.name} is playing with {other_dog.name}!"
		
# instantation
miles = Dog("Miles", 4)
bella = Dog("Bella", 3)

# accessing attributes of an intance
print(miles.name) # Output: Miles
print(miles.age) # Output: 4

# updating an instance's attribute
miles.age = 5
print(miles.age) # Ouput: 5

# calling a method on an instance
print(miles.bark()) # Output: Miles says woof!

# using multiple instances (they are independent from each other)
print(miles.name) # Output: Miles
print(bella.name) # Output: Bella

# interaction between two objects
dog1 = Dog("Buddy", 3)
dog2 = Dog("Max", 4)

print(dog1.play_with(dog2)) # Output: Buddy is playing with Max!
```

-  **passing objects as parameters** = in the `play_with` method, an object of the same class is passed as an argument (`other_dog`), enabling interaction

 **dog and owner relationship**
`Owner` class has a `Dog` class (key word: **has**)

```python
class Dog:
    def __init__(self, name, age):
        self.name = name
        self.age = age

    def bark(self):
        return f"{self.name} says woof!"

class Owner:
    def __init__(self, name, dog):
        self.name = name
        self.dog = dog  # Dog object as an attribute

    def walk_dog(self):
        return f"{self.name} is walking {self.dog.name}."

# Create a Dog object
buddy = Dog("Buddy", 3)

# Create an Owner object with the Dog as an attribute
alice = Owner("Alice", buddy)

# Interaction between Owner and Dog
print(alice.walk_dog())
# Output: Alice is walking Buddy.

# Owner can also access the Dog's behaviors
print(alice.dog.bark())
# Output: Buddy says woof!
```

-  **encapsulation** = the `Owner` class encapsulates the `Dog` class as an attribute, representing a "has-a" relationship
-  **reusable and modular design** = the `Dog` and `Owner` classes are reusable and can be expanded independently
-  **real-world modeling** = the structure reflects real-world scenarios where objects are related hierarchically or depend on one another
